# 任务一：量化评测报告（CPU 仿真、ShareGPT 轨迹与 GPU 引擎 A/B）

> 已确认 `L = prompt token 数 + 生成 token 数`。正式 CPU 合成实验采用 50% prompt 比例。Colab T4 上已完成一组 512 输入 + 128 输出的三轮真实引擎 A/B；长上下文和容量边界仍待实测。

## 方法

主实验使用固定种子 42 的 800 条泊松到达请求，`L` 为 128–1024 token，每条请求的 prompt 约占 `L` 的 50%，模型最大长度 2048 token，块大小 16。逐步扩页方案在到达时分配 prompt 所需 KV 块，生成 token 在请求持续时间内均匀到达。对同一工作负载扫描 500–32000 个 GPU 块，比较连续预留、按最终长度一次性分页、逐步扩页三种方案。正式 CSV 原始结果见 `review_outputs/formal_50pct/results.csv`，图见 `review_outputs/formal_50pct/comparison.svg`。

长上下文实验使用固定种子 2026 的 400 条请求，512、1024、2048、4096 token 各 100 条；每条仍按 50% prompt 比例拆分，按长度分组统计失败率。原始结果见 `review_outputs/formal_50pct/long_context.csv`。

## 指标定义

- **OOM 失败率**：未完成请求数 / 请求总数；动态扩页中的中途失败也计入。
- **平均块占用率**：对观察区间内的 GPU 已占块数 / 容量做时间加权平均。该值表示占用程度，不等于有效 token 比例或吞吐效率。
- **峰值并发**：同时持有请求状态的最大运行请求数；它不是 GPU 实测吞吐量。
- **累计预留块需求**：对每条请求所需块数求和，忽略时间重叠。它可展示按最大长度预留的浪费，不能充当碎片率或实际显存节省率。
- **碎片**：连续分配器的外部碎片可按 `1 - 最大空闲区间 / 总空闲块` 计算；分页分配器的末块未用 token 槽另行统计。两者不能直接混为一个百分比。

## 主要结果

主实验累计预留块需求：连续预留 102400 块，按最终长度分页 29545 块，差值 71.1%。有效 token 总数为 466633；连续预留 1638400 个 token 槽，其中 71.5% 未用；分页预留 472720 个 token 槽，其中末块未用比例 1.3%。原始分子、分母见 `review_outputs/formal_50pct/fragmentation.csv`。在 3000 块容量下，连续预留、一次性分页、逐步扩页的 OOM 失败率分别为 76.5%、21.0%、8.6%；时间加权块占用率分别为 86.7%、82.2%、76.8%，峰值活跃序列数分别为 23、93、118。逐步扩页的峰值包含后来可能失败的请求，不能将其直接视为成功并发上限。在当前离散扫描网格上，三者达到零失败的首个容量分别为 20000、6000、6000 块；这些数值不是精确边界。

长上下文压测显示收益随长度和容量变化。以 1000 块容量为例，4096 token 档的连续预留、一次性分页、逐步扩页失败率分别为 98%、97%、100%；逐步扩页允许更多请求先启动，但长请求可能在后续扩页时失败，因此不能只以到达时准入率判断方案优劣。全部档位与容量的结果应直接从 CSV 复核。

## ShareGPT 真实对话长度轨迹

另以固定数据集 `anon8231489123/ShareGPT_Vicuna_unfiltered` 的 `ShareGPT_V3_unfiltered_cleaned_split.json`（revision `192ab2185289094fc556ec8ce5ce1e8e587154ca`，SHA-256 `35f0e213ce091ed9b9af2a1f0755e9d39f9ccec34ab281cd4ca60d70f6479ba4`）构造 800 条数值请求。使用 `Qwen/Qwen2.5-1.5B-Instruct` 的固定 tokenizer revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`，按模型 chat template 计算每轮 prompt token 数，并按回复文本计算生成 token 数；随机种子 42，筛选总长度 128–4096 token。原始对话文本未写入输出轨迹。ShareGPT 原文件没有到达时间与持续时间，这两项仍按固定种子的泊松到达和均匀持续时间合成，不能称为真实线上流量时序。

轨迹总长度范围 131–4033 token，中位数 989 token，实际 prompt token 占总长度 69.7%。这不是 50% prompt 合成主实验的重复实验。三种方案使用同一条轨迹与 16-token 块；连续基线为每条序列按 4096 token 上限预留。在 6000 块容量，连续预留、一次性分页、逐步扩页的失败率依次为 78.9%、19.1%、12.1%；在 9000 块容量依次为 68.1%、2.1%、0.25%。扫描网格上分页两种方案在 12000 块首次零失败，连续预留至 32000 块仍有 3.6% 失败。轨迹累计有效 token 为 887800，连续预留槽的未用比例为 72.9%，分页末块未用比例为 0.68%。这些仍是 CPU 元数据仿真值，且两种未用比例的分母分别是各自预留的 token 槽。

## Colab T4：真实引擎三轮 A/B

同一张 Tesla T4（15,360 MiB，GPU UUID `GPU-1d320edd-f5e3-da67-7540-e7d84812a199`）上，使用固定模型 revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`、float16、512 输入 token、128 生成 token、4096 最大上下文。输入 token ID 哈希在六次运行中相同。Transformers 5.20.2 使用每批新建的 `StaticCache(max_cache_len=4096)`；vLLM 0.33.0 使用 16-token 块，`gpu_memory_utilization=0.9`，关闭前缀缓存。两侧均用 PyTorch 2.14.0+cu132，每批计时前预热两次；每侧在新进程中运行三轮。原始证据见 `review_outputs/gpu_formal/main_512_128/`，原 ZIP SHA-256 为 `c6f752e0bd914d73b16c5727508b4c4db037e8b2d2a6ed7995414f5e8e3044ef`。

这组结果说明在上述配置和批量下 vLLM 引擎的生成吞吐高于 Transformers StaticCache 基线；两引擎的调度、算子、CUDA graph、KV 池预留方式均不同，不能把吞吐差异归因于分页本身，也不能将两列设备显存差称为分页节省的显存。vLLM 预留接近 0.9 的设备预算，故其设备已用显存更高；这里不能据此判定 KV 内部利用率。还需长上下文、预算与压力扫描才能评估 OOM 边界和实际并发。

## 可复现性与局限

运行 `python run_experiment.py` 重算正式 50% 结果；`python run_experiment.py --sensitivity` 重算 25%、50%、75% 三档敏感性分析，已安装 matplotlib 时还生成 PNG。运行 `python -m unittest discover -s tests -v` 执行单测，`python tests/measure_coverage.py` 检查覆盖率。2026-11-09 的本地验证为 37 个单测通过，整个 `kv_cache` 包可执行行覆盖 477/629（75.8%）。引入显式位图块池后重跑正式 CPU 主实验，`results.csv`、`fragmentation.csv`、`long_context.csv` 的 SHA-256 均与改动前一致。

CPU 主实验与 ShareGPT 轨迹均为元数据仿真；GPU 章节是实际推理引擎比较，本项目分配器没有控制真实 KV 张量。现有 GPU 数据只覆盖一个输入/输出长度、五个提交批量和三轮重复；未测长上下文 OOM、KV 预算敏感性、实际同时活跃序列数或真实 KV 换出成本。单批 smoke test 的原始文件仍保留于 `review_outputs/gpu_setup/smoke_evidence/`，不纳入三轮均值。
